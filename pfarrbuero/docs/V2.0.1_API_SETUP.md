# Pfarrbüro-KI V2.0.1 – Secure API / Betriebs- und Integrationshinweise

## Zielarchitektur

Die Windows-Desktop-GUI greift nicht mehr direkt auf PostgreSQL zu. Sie kommuniziert per HTTPS mit dem FastAPI-Service. Nur der API-Service besitzt die Datenbankverbindung und setzt den Tenant-Kontext innerhalb jeder Repository-Transaktion.

```text
Windows-GUI
  | HTTPS + Bearer Access Token
  v
FastAPI (/v1/*)
  | OIDC/JWKS Tokenprüfung
  | serverseitige Ableitung von sub / tenant_id / org_unit_id
  | RBAC-Prüfung im Repository
  v
PostgreSQL 16 + Row-Level Security + Audit
```

## Verbindliche Serverkonfiguration

Der API-Host benötigt:

- `PFARRBUERO_DATABASE_URL`: PostgreSQL-DSN eines dedizierten Runtime-DB-Benutzers mit minimalen Rechten.
- `PFARRBUERO_OIDC_ISSUER`: exakter Issuer des OIDC-Providers.
- `PFARRBUERO_OIDC_AUDIENCE`: Audience, für die das API-Access-Token ausgestellt wurde.
- `PFARRBUERO_OIDC_JWKS_URL`: HTTPS-JWKS-Endpunkt des vertrauenswürdigen Providers.

Das verifizierte JWT muss enthalten:

- `sub`: stabile Benutzer-ID, die einem aktiven Benutzer in der Pfarrbüro-Datenbank entspricht.
- `tenant_id`: serverseitig vom Identity Provider vergebener Mandantenkontext.
- `org_unit_id`: serverseitig vergebener Organisationsbereich.
- `iss`, `aud`, `exp`, `iat`: reguläre JWT-/OIDC-Claims.

Die Claims `tenant_id` und `org_unit_id` müssen durch den Identity Provider bzw. einen vertrauenswürdigen Claims-Enrichment-Prozess gesetzt werden. Sie dürfen nicht ungeprüft aus frei editierbaren Client-Parametern oder HTTP-Headern übernommen werden. Das API akzeptiert ausschließlich RS256-Signaturen mit Schlüssel aus dem konfigurierten JWKS-Endpunkt; Issuer, Audience und Ablauf werden geprüft.

## API starten (Entwicklung)

Im Verzeichnis `pfarrbuero`:

```powershell
python -m pip install -r requirements.txt
uvicorn api:app --host 127.0.0.1 --port 8080
```

Für einen Serverbetrieb ist TLS am Reverse Proxy verpflichtend. Den API-Port nicht ungeschützt im Internet veröffentlichen. PostgreSQL darf nur vom API-Host erreichbar sein.

## Desktop konfigurieren

Die Desktop-Anwendung benötigt:

- `PFARRBUERO_API_URL`: Basis-URL des API-Service, z. B. `https://pfarrbuero-api.example.invalid`.
- `PFARRBUERO_ACCESS_TOKEN`: gültiges OIDC-Access-Token mit den oben beschriebenen Claims.

Die Übergabe des Tokens per Umgebungsvariable ist nur ein Entwicklungs-/Integrationsmechanismus. Vor einem Pilotbetrieb ist ein interaktiver OIDC-Authorization-Code-Flow mit PKCE und sichere Tokenablage im Windows Credential Manager umzusetzen. Tokens dürfen nicht in Logs geschrieben werden.

Wenn nur `PFARRBUERO_DATABASE_URL` konfiguriert ist, verweigert die GUI den Datenbankbetrieb. Es gibt keinen direkten DB-Fallback. Ohne API- oder DB-Konfiguration startet ausschließlich der ausdrücklich gekennzeichnete lokale SQLite-Demo-Modus.

## Endpunkte

| Methode | Pfad | Zweck |
|---|---|---|
| GET | `/healthz` | Prozess-/Liveness-Prüfung, ohne Datenbankzugriff |
| GET | `/v1/me` | verifizierte Benutzer- und Mandantenidentität |
| GET | `/v1/cases` | Vorgänge gemäß Tenant-RLS und RBAC lesen |
| POST | `/v1/cases` | Vorgang anlegen; Audit wird im Repository atomar geschrieben |

Die API-Dokumentationsendpunkte sind im Entwicklungsstand deaktiviert. Berechtigungsfehler werden als HTTP 403, fehlende/ungültige Tokens als HTTP 401 beantwortet.

## Sicherheitsgrenzen / noch offen

V2.0.1 ist ein Architektur- und Integrationsschritt, keine Produktivfreigabe:

1. Noch kein interaktiver OIDC-Login/PKCE-Client in der Windows-GUI.
2. Claims-Mapping und Mandantenwahl müssen mit dem konkreten Identity Provider abgestimmt und gegen Manipulation getestet werden.
3. Noch kein produktiver Reverse-Proxy-/TLS-/Rate-Limit-/Monitoring-Stack.
4. Kein Windows Credential Manager Token Store.
5. API-Routen für die sechs Fachmodule sind noch nicht implementiert.
6. Rollen- und Seelsorgegeheimnis-Prüfung greift derzeit im vorhandenen Vorgangs-Repository; weitere Ressourcen benötigen eigene zentrale Policy-Tests.
7. Keine produktiven Pfarr-, Sakramenten- oder Seelsorgedaten verwenden, bevor Datenschutz, Berechtigungen, Backup/Restore und Penetrationstest freigegeben sind.

## Prüfumfang in CI

- fehlendes Bearer-Token wird abgewiesen
- Identitätsantwort basiert auf verifiziertem Principal
- Tenant, Organisationseinheit und Benutzer-ID werden aus dem Principal in die Repository-Konfiguration übernommen
- API-Routen geben Repository-Berechtigungsfehler als 403 zurück
- vorhandene PostgreSQL-16-Tests prüfen RLS, Mandantentrennung, Least Privilege und Audit
