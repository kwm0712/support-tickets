# Pfarrbüro-KI V2.0.2 – OIDC-Anmeldung mit PKCE

## Zielbild

Die Windows-GUI startet den OIDC Authorization Code Flow mit PKCE (S256) im Standardbrowser. Der Identity Provider leitet den Browser an einen kurzlebigen Loopback-Callback auf 127.0.0.1 zurück. Die Desktop-Anwendung tauscht den Authorization Code mit dem Code Verifier am Token-Endpunkt ein.

- Kein Client Secret in der Desktop-Anwendung (Public Client).
- Zufälliger state schützt den Callback vor CSRF/Response Injection.
- Zufälliger nonce wird im ID-Token geprüft.
- ID-Token-Signatur wird über den JWKS-Endpunkt mit RS256 geprüft; Issuer, Audience, exp, iat und nonce werden validiert.
- Access Token bleibt im Arbeitsspeicher und wird für API-Aufrufe bei Bedarf erneuert.
- Refresh Token wird über keyring im Windows Credential Manager (Windows Vault) gespeichert.
- Logout löscht den gespeicherten Refresh Token.

## OIDC-Provider konfigurieren

In der Registrierung des Identity Providers einen nativen/publicen OIDC-Client anlegen:

- Client-Typ: Public / Native
- Authorization Code Flow: aktiviert
- PKCE: S256 verpflichtend
- Client Secret: keines
- Scopes: `openid profile offline_access`
- Redirect-URI: Loopback `http://127.0.0.1:<dynamischer-Port>/callback`; der Provider muss dynamische Loopback-Ports für 127.0.0.1 unterstützen oder einen festen, providerkonformen Loopback-Port erlauben.

Der Access Token für die Pfarrbüro-API muss zusätzlich die serverseitig gemappten Claims `tenant_id` und `org_unit_id` enthalten. Diese Claims müssen aus dem Identity-/Mandantenverzeichnis kommen und dürfen nicht aus frei editierbaren Client-Parametern übernommen werden. Die API prüft den Access Token weiterhin selbständig.

## Windows-Konfiguration

Für die Desktop-Anwendung:

- `PFARRBUERO_API_URL`: HTTPS-Basisadresse des Pfarrbüro-API-Service.
- `PFARRBUERO_OIDC_ISSUER`: exakter Issuer aus dem Discovery-Dokument.
- `PFARRBUERO_OIDC_CLIENT_ID`: Client-ID des Public Clients.
- optional `PFARRBUERO_OIDC_SCOPE`: Standard `openid profile offline_access`.

Die Desktop-Anwendung lädt die Discovery-Metadaten unter `{issuer}/.well-known/openid-configuration`. Authorization-, Token- und JWKS-Endpunkt müssen HTTPS verwenden (HTTP ist nur für localhost/127.0.0.1 in lokalen Entwicklungsumgebungen erlaubt).

## Ablauf

1. Benutzer klickt in der COMPELEC ONE GUI auf **Anmelden**.
2. Die Anwendung startet einen lokalen Callback-Listener auf 127.0.0.1 und öffnet den Browser.
3. Der Identity Provider authentifiziert den Benutzer (MFA/Conditional Access nach Provider-Konfiguration).
4. Der Browser ruft den Loopback-Callback mit Authorization Code und state auf.
5. Die Anwendung prüft state und tauscht den Code mit PKCE-Verifier ein.
6. Die Anwendung prüft das ID-Token einschließlich Signatur und nonce.
7. Der API-Client verwendet den Access Token; bei Ablauf wird das Refresh Token aus Windows Vault zum Erneuern genutzt.
8. **Abmelden** löscht den Refresh Token und beendet die lokale Sitzung.

## Einschränkungen / Freigabekriterien

- Der konkrete Identity Provider wurde noch nicht gegen die Loopback-Redirect-Registrierung und Claims-Mappings integriert getestet.
- Der API-Access-Token muss `sub`, `tenant_id` und `org_unit_id` als gültige UUID-Claims enthalten; das ID-Token allein wird nicht für API-Aufrufe verwendet.
- Die GUI erwartet Windows; der sichere Token-Speicher ist explizit auf Windows Vault festgelegt.
- Das automatische Refresh setzt voraus, dass der Provider bei `offline_access` ein Refresh Token ausstellt und Rotation korrekt unterstützt.
- Kein produktiver Betrieb ohne TLS, Provider-Konfiguration, Rechte-/Mandantenprüfung, Datenschutzfreigabe und Security Review.
- Bis zur Abnahme ausschließlich Testmandanten und synthetische Daten verwenden.
