# Pfarrbüro-KI V2.0.3 – Mandanten- und Administrationsverwaltung

## Zielbild
V2.0.3 ergänzt den V2.0.2-OIDC-Stand um serverseitige Administrationsendpunkte. Die GUI bleibt API-Client; Mandanten-, Organisations-, Benutzer- und Rollenentscheidungen liegen in API und PostgreSQL.

Organisationshierarchie: Bistum → Pastoraler Raum → Pfarrei → Pfarrbüro. Verwendet werden die vorhandenen Tabellen parish_tenants, parish_org_units, parish_users, parish_memberships, parish_roles, parish_permissions und parish_audit_events. Die Migration 0001 ist Voraussetzung; für die Endpunkte ist keine Schemaänderung erforderlich.

## API
- GET/POST /v1/admin/org-units
- GET/POST /v1/admin/users
- GET /v1/admin/roles
- POST /v1/admin/memberships

Jede Route erfordert ein verifiziertes Bearer-Token. Berechtigungen: org.read, org.admin, user.admin; die Vergabe von bistum_admin erfordert zusätzlich tenant.admin. Die Zielorganisation muss innerhalb des Verwaltungsbereichs liegen. Änderungen und Audit-Ereignisse erfolgen in derselben PostgreSQL-Transaktion.

## Microsoft Entra ID – Zielkonfiguration
- Für den ersten Bistums-Pilot zunächst Single-Tenant-App-Registrierung, Public Client.
- Authorization Code Flow mit PKCE S256; kein Client Secret in der Desktop-App.
- Loopback Redirect URI 127.0.0.1 mit dynamischem Port gemäß OIDC-Client.
- Separate API-App-Registrierung / Expose an API; Desktop-Client erhält nur delegierte API-Berechtigung.
- MFA und Conditional Access durch den Bistums-Tenant administrieren.
- Entra-Identität (iss + tid + oid) serverseitig einer lokalen parish_users-Identität zuordnen. Entra tid ist der Microsoft-Verzeichnismandant und darf nicht mit dem fachlichen Bistumsmandanten verwechselt werden.
- Keine tenant_id, org_unit_id, Rollen oder Berechtigungen aus frei editierbaren Client-Parametern übernehmen. Fachlichen Mandanten- und Organisationskontext ausschließlich serverseitig ableiten.

## Kritisches Release-Gate
Der vorhandene V2.0.2-Tokenvalidator erwartet aktuell UUID-Werte in sub, tenant_id und org_unit_id. Ein unverändertes Entra-ID-Token erfüllt diese projektspezifische Annahme nicht zuverlässig. Vor einem echten Entra-Pilot ist eine serverseitige Identity-Mapping-Stufe erforderlich: Entra iss + tid + oid → lokale Benutzer-ID → aktive Mitgliedschaft → fachlicher Mandant und Organisation. Das ist ausdrücklich noch nicht umgesetzt.

Die Runtime-DB-Rolle aus dem bestehenden CI-Fixture besitzt aktuell keine vollständigen Schreibrechte auf parish_users und parish_memberships. Vor Integrationstests und Betrieb müssen die minimal notwendigen INSERT/UPDATE-Rechte sowie RLS-Policies kontrolliert ergänzt werden. Keine pauschalen Tabellenrechte vergeben.

## Definition of Done
- API-Unit- und PostgreSQL-Integrationstests grün.
- Mandantenfremde Lese- und Schreibzugriffe technisch blockiert.
- Administration nur innerhalb der zugewiesenen Organisationshierarchie.
- Rolleneskalation serverseitig ausgeschlossen.
- Audit-Ereignis atomar mit jeder administrativen Änderung.
- Entra-Mapping und MFA in einem echten Testtenant verifiziert.
- Windows-GUI zeigt Admin-Funktionen nur bei passender API-Berechtigung.
- Windows-EXE und Installer gebaut, gestartet und mit SHA-256 dokumentiert.

Bis dahin ausschließlich synthetische Pilotdaten verwenden.
